# معماری فعلی تیشه r0.2

## دامنه اجرا

Laravel 12، PHP، Eloquent، Blade و درایور mysql. محیط تحویل MariaDB است؛ دیتابیس SQLite فقط برای suite پیش‌فرض تست است. سرویس خارجی مالی یا SMS فعال نیست. توکن‌های برند در ابتدای `public/css/reference.css` و مؤلفه‌های قابل استفاده مجدد در `resources/views/components` قرار دارند.

## لایه‌ها

```text
HTTP → session / CSRF / محدودیت نرخ / حساب فعال
     → مجوز نقش و FormRequest
     → Policy مالکیت یا کنترل مشارکت در گفتگو/سفارش
     → Controller → Service → DB transaction / Eloquent
     → AuditService و NoticeService
     → Blade با escape پیش‌فرض
```

سرویس‌ها:

- RegistrationService: ایجاد اتمیک حساب و پروفایل.
- ListingService: ثبت و ویرایش آگهی، تصویر محصول و اعلام آمادگی یکتا.
- UploadedImageService: اعتبارسنجی قبلی فایل، decode و re-encode به WebP و نام تصادفی.
- AdminService: تغییر وضعیت/اطلاعات کاربر، بررسی آگهی، دسته‌بندی، پاسخ گزارش و تنظیمات؛ همه همراه audit و transaction.
- OrderService: قفل خریدار و محصول، کنترل موجودی و قیمت، سفارش idempotent، رزرو/برگشت موجودی و گردش وضعیت نقش‌محور.
- NoticeService: اعلان دیتابیسی واقعی؛ هیچ SMS/Push یا job مالی ارسال نمی‌کند.
- AuditService: رویدادهای قابل مشاهده در مدیریت. مدل AuditLog append-only است؛ SQL مستقیم هنوز می‌تواند آن را دور بزند و لاگ مستقل زیرساخت لازم است.

## مدل داده افزوده‌شده

| جدول | رابطه و معنا |
|---|---|
| conversations | آغازکننده و صاحب آگهی؛ unique روی آغازکننده/نوع آگهی/شناسه آگهی |
| messages | پیام متنی متعلق به گفتگو و فرستنده |
| notifications | ساختار استاندارد database notifications لاراول؛ داده و read_at |
| reports | کاربر گزارش‌دهنده، نوع/شناسه موضوع، دلیل، وضعیت، مسئول و پاسخ |
| content_pages | slug یکتا، متن و وضعیت انتشار |
| material_orders | خریدار، فروشنده، UUID پیگیری، idempotency خریدار، جمع کالا/حمل/مجموع و وضعیت |
| material_order_items | snapshot نام، برند، واحد، قیمت و مقدار؛ ارتباط محصول اصلی |
| order_events | actor، مرحله سفارش و یادداشت برای پیگیری |

جداول پایه users، roles، permissions، permission_role، user_profiles، countries، seller_locations، job_categories، job_requests، job_applications، material_categories، material_products، product_images، audit_logs و settings حفظ شده‌اند؛ جدول‌های framework شامل sessions/cache/queue نیز وجود دارند. `jobs` مربوط به queue است، نه کاریابی؛ درخواست کار در `job_requests` قرار دارد.

ساختار مرجع در `schema-reference.sql` خروجی MariaDB بدون داده است؛ برای نصب از Migration استفاده کنید، نه import این فایل.

## وضعیت‌ها و قواعد

### سفارش مستقیم

```text
awaiting_seller ──seller──→ confirmed → ready_to_ship → shipped ──buyer──→ delivered
        │                       │
        └─buyer/seller→ cancelled←seller
```

- وضعیت‌های انتقال در Service با سطر قفل‌شده کنترل می‌شوند. مدیر فقط ناظر است.
- موجودی با ثبت سفارش کم و هنگام لغو مجاز یک بار برگردانده می‌شود.
- رزرو فعلی timeout خودکار ندارد؛ رهاسازی با لغو مجاز انجام می‌شود.
- snapshot قیمت در order item از داده سرور است؛ تغییر محصول، snapshot قبلی را عوض نمی‌کند.
- idempotency برای هر خریدار یکتا است؛ تکرار همان key روی همان کالا همان سفارش را برمی‌گرداند. برای قصد خرید جدید باید key جدید باشد.
- مبلغ integer و ریالی است؛ رابط تومان نشان می‌دهد. حمل null با رایگان یکی نیست.
- payment_method همیشه direct و payment_status همیشه unverified_external است؛ تحویل یا تأیید تجاری، مدرک پرداخت بانکی نیست.
- تغییر حمل در تأیید فروشنده آشکار نمایش داده می‌شود؛ توافق نهایی خریدار پیش از پرداخت مستقیم ضروری است. گردش پذیرش تغییر مبلغ جداگانه هنوز اضافه نشده است.

### پیام‌ها

شروع از آگهی published و متعلق به حساب فعال، با فرستنده‌ای غیر از صاحب آگهی ممکن است. خواندن و نوشتن فقط برای دو مشارکت‌کننده است؛ نقش مدیر به‌خودی‌خود دسترسی به گفتگو نمی‌دهد. محتوای پیام در audit ثبت نمی‌شود؛ فقط رویداد ارسال و شناسه گفتگو ثبت می‌شود. این حفاظت دسترسی است، نه رمزنگاری سرتاسری. خواندن، زمان last message را عوض نمی‌کند. پیام‌ها صفحه‌بندی ۵۰تایی دارند و بلادرنگ نیستند.

### گزارش و محتوا

گزارش آگهی فقط برای رکورد قابل مشاهده توسط گزارش‌دهنده قابل ثبت است. گزارش پشتیبانی موضوع عمومی ندارد. مدیر با پاسخ، مسئول رسیدگی و وضعیت reviewing/resolved/dismissed را ثبت و اعلان ایجاد می‌کند؛ کاربر فقط گزارش‌های خود را می‌بیند. متن صفحات منتشرشده با escape نمایش داده می‌شود و HTML ارسالی اجرا نمی‌شود.

### مدیریت

فقط مجوز admin.access اجازه ورود می‌دهد. نقش، رمز و زمان تأیید موبایل از فرم ادمین قابل تغییر نیست. حساب مدیر محافظت‌شده است. تعلیق، نشست را حذف و آگهی‌ها را از جستجو/مشاهده عمومی خارج می‌کند. دسته دارای آگهی قابل حذف نیست. لاگ CSV تا ۵۰۰۰ ردیف خروجی می‌دهد و سلول‌های شبیه فرمول خنثی می‌شوند. تنظیمات فقط whitelist عمومی را می‌پذیرند؛ فعال‌سازی پول از فرم ممنوع است.

## امنیت و الزامات باقی‌مانده

کنترل‌های حاضر: CSRF، هش رمز، rotate نشست، Session encryption، HttpOnly/Secure در HTTPS، Eloquent binding، escape Blade، Policy، کنترل مشارکت، محدودیت نرخ و تصویر re-encode‌شده. CSP منابع محلی و HSTS روی HTTPS تنظیم می‌شود.

در پیش‌نمایش، `TRUSTED_PROXIES=*` و `CSP_FRAME_ANCESTORS=*` فقط برای سازگاری پراکسی/iframe محیط است؛ در تولید پراکسی‌ها را محدود و frame-ancestors را به self/allowlist تغییر دهید. DocumentRoot فقط public و اجرای PHP در upload ممنوع باشد.

تست واقعی چند اتصال همزمان، load، ممیزی نفوذ، MFA، سیاست نگهداری/حذف داده و audit مستقل هنوز انجام نشده‌اند. تماس/موبایل، تخصص و اطلاعات آگهی احراز نشده‌اند. داده خام کارت دریافت نمی‌شود. هیچ مدل یا ledger مالی ناقصی به‌عنوان پول واقعی ارائه نشده است.

بین‌المللی: IR فعال و IQ غیرفعال در جدول countries؛ زمینه locale/currency وجود دارد، اما شماره تلفن و زبان فعال فعلاً فقط ایران/فارسی است. عراق بدون بررسی مستقل حقوقی و provider نباید فعال شود.
